# HabitHero 孩子角色、加入天數與儀表板規則

> 狀態：討論稿
>
> 本文件先定義產品邏輯與資料契約，尚未代表全部功能已實作。

## 1. 本次決策

- 家長新增孩子時，必須選擇性別／角色分類。
- 系統依分類顯示可選角色。
- 角色在建立孩子時選定，建立後目前不提供更換入口。
- 角色資料使用獨立的 `character_id`，不要只依賴性別推導角色。
- 儀表板左上角在點數左側新增「加入天數」。
- 加入天數從孩子資料建立日開始計算，不從孩子登入帳號建立日開始計算。
- 儀表板統計數字使用黑色文字；標籤可以維持原本的層次與顏色。

## 2. 新增孩子流程

建議流程順序：

1. 輸入孩子名稱。
2. 選擇性別／角色分類。
3. 從該分類的角色清單選擇一個角色。
4. 輸入孩子登入帳號與密碼。
5. 通過家長同意與欄位驗證後建立。
6. 儲存孩子資料、角色資料與建立時間。

建立按鈕只有在以下條件全部成立時才可執行：

- 名稱不為空白，且符合長度限制。
- 性別／角色分類已選擇。
- `character_id` 存在，且屬於所選分類。
- 帳號名稱格式正確且未被使用。
- 密碼與確認密碼符合現有規則。
- 家長已完成必要的同意流程。
- 目前沒有另一個孩子建立請求正在送出。

如果建立途中失敗，不能留下半套資料。帳號建立成功但孩子資料建立失敗時，應清理剛建立的帳號，讓家長可以安全重試。

## 3. 性別與角色資料設計

第一版可以提供：

- 男孩
- 女孩

程式資料應保持可擴充：

```ts
type ChildGender = 'boy' | 'girl';

type CharacterOption = {
  id: string;
  name: string;
  gender: ChildGender;
  imageUrl: string;
  thumbnailUrl: string;
  isActive: boolean;
  sortOrder: number;
};
```

孩子資料至少需要保存：

```text
gender
character_id
```

`gender` 用於建立流程的篩選與資料記錄；`character_id` 才是儀表板實際顯示角色的唯一來源。不要在每次渲染時使用性別重新挑選角色，否則新增角色或調整排序可能導致既有孩子的角色改變。

未來如果加入中性角色、限定角色或其他分類，可以擴充角色資料，不需要更改既有孩子的 `character_id`。

## 4. 角色鎖定規則

角色與性別在孩子建立成功時固定：

- 新增孩子頁面可以選擇。
- 孩子設定頁目前不顯示修改性別或角色的控制項。
- 儀表板依照已儲存的 `character_id` 顯示。
- 刪除孩子後重新建立，視為新的孩子資料，加入天數與角色重新開始。
- 未來若開放更換角色，應視為獨立功能，不要讓新增角色自動套用到既有孩子。

這裡的「不能更換」是資料與操作規則，而不是依靠前端隱藏按鈕來保護。後端建立與更新 API 也應拒絕目前未允許的角色修改。

## 5. 加入天數定義

### 顯示名稱

第一版顯示：

```text
加入天數
12 天
```

「加入天數」代表孩子加入這個家庭後經過的日曆天數，不代表完成任務天數，也不會因為某天沒有完成任務而歸零。

### 起算時間

優先使用孩子資料的 `created_at`。目前孩子可能先建立資料、之後才由家長建立登入帳號，因此不能使用登入帳號的建立時間。

如果未來資料匯入、轉移或允許修改建立時間，建議新增不可變的 `joined_at` 欄位，並以它作為產品語意上的正式起算時間。

### 計算方式

以 Asia/Taipei 時區的日期計算，不用瀏覽器當地時區：

```text
加入日當天 = 1 天
隔天 = 2 天
```

可用概念公式表示：

```text
加入天數 = TaipeiToday - TaipeiDate(joined_at) + 1
```

顯示值必須至少為 `1`。如果資料時間在未來、時間格式無效或資料缺失，不應顯示負數或 `NaN`；應採用安全 fallback 並記錄錯誤。

### 日期切換觸發

- 使用者開啟儀表板時重新計算。
- App 回到前景時重新計算。
- 若頁面持續開啟跨過台北午夜，隔天應更新一次，不需要使用者重新登入。
- 不需要為每天建立一筆資料；加入天數是由固定日期衍生的顯示值。

## 6. 左上角統計排列

建議固定為：

```text
加入天數        點數
12 天            240
```

規則：

- 加入天數放在點數左側。
- 兩個統計項目的順序在家長與孩子儀表板保持一致，避免不同視角產生認知負擔。
- 主要數字為黑色。
- 單位「天」與「點」可以使用黑色或深灰色。
- 標籤文字不必全部改黑，保留標籤與數字的視覺層級。
- 小尺寸螢幕不可因新增統計造成水平溢出。
- 統計值變動時不應改變卡片寬度或造成整個頁面跳動。

## 7. 任務與點數觸發規則

這些狀態要分開處理，避免把「孩子完成」和「獲得點數」混為一談：

| 事件 | 是否增加點數 | 是否影響加入天數 |
| --- | ---: | ---: |
| 家長建立任務 | 否 | 否 |
| 孩子開始任務 | 否 | 否 |
| 孩子送出任務 | 否 | 否 |
| 家長核准任務 | 是 | 否 |
| 家長退回任務修改 | 否 | 否 |
| 孩子兌換獎勵 | 扣除點數 | 否 |
| 家長手動調整點數 | 依調整方向 | 否 |
| 孩子登入 | 否 | 否 |
| 日期跨日 | 否 | 加入天數重新計算 |

點數增加應以後端核准流程為準，並且與 point ledger 同一個交易完成。前端不能只因為按下「完成」就先把點數加上去。

## 8. 需要特別處理的例外情境

### 建立流程

- 連續點擊建立按鈕不可產生兩個孩子。
- 家長同意尚未完成時，不應先建立孩子資料。
- 帳號名稱被使用時，保留表單內容，讓家長只修改帳號名稱。
- 角色圖片載入失敗時，仍要有可辨識的 fallback 圖片，不能出現空白選項。
- 角色已下架時，既有孩子仍要能顯示原角色；只有新建孩子不能再選下架角色。

### 家庭與帳號

- 孩子資料建立成功但尚未綁定登入帳號時，加入天數仍從孩子資料建立日開始。
- 家長刪除孩子時，相關任務、獎勵、願望、點數與登入帳號依現有刪除規則一起處理。
- 家庭切換時，加入天數必須使用目前選中孩子自己的建立時間，不可沿用上一個孩子的統計。
- 讀取資料尚未完成時，不要把加入天數暫時顯示成 0 造成誤解；可顯示載入狀態。

### 日期與同步

- 伺服器時間與裝置時間不同時，以產品指定的 Asia/Taipei 日期為準。
- 離線時可以暫時使用最後已載入的資料，但重新連線後要重新計算。
- 不應將加入天數寫回資料庫作為每日累加值，避免重複計算與同步衝突。

## 9. 建議的實作順序

1. 擴充 `child_profiles` 的性別與 `character_id` 欄位。
2. 建立角色 catalog 與角色圖片資產。
3. 更新新增孩子表單與建立 API，加入後端驗證。
4. 將角色資料接到孩子儀表板顯示。
5. 將加入天數加入 child view model。
6. 更新儀表板左上角統計排列與數字顏色。
7. 補上日期切換、重複送出、失敗回滾與角色鎖定測試。
8. 在 375x709 與 1440x900 檢查角色選擇、統計排列與 overflow。

## 10. 驗收條件

- 新增孩子時沒有選分類或角色不能建立。
- 男孩只能看到男孩角色，女孩只能看到女孩角色。
- 建立成功後，重新整理、登出登入、切換家庭，角色仍相同。
- 角色 catalog 排序或新增角色，不會改變既有孩子角色。
- 加入當天顯示 1 天。
- 跨過台北午夜後，加入天數增加 1。
- 尚未建立登入帳號的孩子，也能正確顯示加入天數。
- 任務送出不增加點數，家長核准後才增加點數。
- 點數兌換成功後才扣除點數，失敗不能扣點。
- 統計數字為黑色，手機畫面不水平溢出。
